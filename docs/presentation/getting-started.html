Sign a Yocto build
without holding the keys

meta-laavat is a Yocto layer that makes signing a step of the build. A recipe you already own gains one inherit line; the task it brings uploads the artifact to a LAAVAT signing service, gets it back signed, checks it, and lets the build carry on. The private key stays in a hardware security module and never reaches the builder, CI, or this layer. This page is what the layer does, what it costs per board, what it proves, and how to run the whole thing yourself - the first two paths need no account.

In one minute

The problem

Signing firmware needs a private key. Put that key on a build machine or in a CI runner and one leak lets someone else sign firmware your devices will accept as genuine.

What this does

A do_laavat_sign task sits in the recipe's own graph between whatever builds the artifact and whatever consumes it. It uploads the artifact, waits for approval, downloads the result and checks two digests before writing the output: that the download is what the service reported, and that the request covers the file this build uploaded. Any failure leaves the output absent, so the build stops rather than shipping unsigned. The signing key itself is generated as non-exportable in the service's hardware security module, which performs signatures inside itself; no operation the service offers exports it.

What it costs to adopt

A layer added to your build, and one inherit line per artifact you want signed, on a bbappend of a recipe you already own. The class knows which file goes up and where the signed one lands; you supply the product and operation ids and, where the device must trust a key, its fingerprint. Measured across ten sample boards: 8 to 12 lines that mention laavat in each, 27 to 42 lines of glue in all once the layer.conf and the RAUC bundle recipe are counted, and no Python. How you fetch layers and which distro you use do not change; your build host gains a network dependency, a token file and a handful of variables. There is no offline mode, and an unreachable service stops the build rather than shipping something unsigned - recoverably, without spending a second approval. The layer is public on GitHub, and the client it drives, signing-tool, comes from PyPI through the layer's own recipe.

Where it stands

Four artifact types have classes: boot image, kernel, trusted applications and update bundle. On an emulated Arm64 board, three of them - kernel, trusted applications, update bundle - are verified at runtime against the service's key by U-Boot, OP-TEE and RAUC, each paired with a tampered copy that is refused. The boot image is checked at build time only, because the chip's boot ROM checks it against a hash fused into the silicon, which no emulator models. Glue exists for ten boards from five vendors; the runtime evidence here comes from the emulated one, and no physical board has booted service-signed firmware yet. "So what happens to the R&D keys?" below has it per artifact.

What this is

#

You already have a Yocto build for your board that works. That is the starting point this is designed around. meta-laavat adds signing to that build and changes nothing else about it - not how you fetch layers, not your distro, not your image recipe. It is one layer of ten bbclasses (plus two internal helpers they share) with no Python in it, and it knows nothing about machines or boards: adding it to BBLAYERS is genuinely inert until one of your recipes inherits one of its classes. That is what makes it safe to drop into a BSP that already works.

Two things travel with it. signing-tool is the LAAVAT client, published on PyPI; the classes call it as an ordinary command, so the protocol lives there rather than in your build system. meta-laavat-testbed is a complete Yocto build with every signing path already wired - it exists so you can watch the mechanism run on someone else's board before touching your own, and most of this page is a tour of it for exactly that reason.

So: the layer's docs/INTEGRATION.md is the walkthrough for your build, target by target. This page is the one that shows you what you would be adopting first.

SCOPE

What gets signed

#

Four artifact types have a class of their own, the boot image in three formats. They are not all proven to the same depth, and the difference is the first thing to understand about it. (An operation below is the service's unit of signing capability - one operation, one key behind it.)

why the boot image is verified differently

Every other artifact is verified by software this build produces, so the demo can boot it and watch. The boot image is verified by the silicon, against a key hash burned irreversibly into fuses. Burning those fuses is a one-way door on a real board, which is why the boot image stops at build-time verification here and why the last step of adopting it is yours.

MECHANISM

What happens during a build

#

Nothing is signed after the build. do_laavat_sign is a task in the recipe's own graph, flagged [network] = "1", sitting between whatever produces the artifact and whatever consumes it. Its body is one signing-tool imagesigning sign call: the four steps below happen inside the client, and the class only assembles the command line.

why the HSM is the whole point

A Hardware Security Module is purpose-built tamper-resistant hardware whose defining property is that a key can be generated inside it as non-exportable. The service's signing keys are generated that way, and no operation the service offers exports them. Software asks the HSM to sign; it returns a signature. The key is never handed to the builder as a file that can be copied.

That is what changes the blast radius. A build machine holding a signing key is one compromise away from an attacker signing their own firmware for your devices, and you would not necessarily know. A build machine talking to an HSM can, at worst, get things signed while it is compromised - a serious outcome, but one that is recorded in the service's request log, stoppable by revoking a token, and preventable by four-eyes approval, under which a person approves each request. The key survives the incident. Be clear which mode you run: every example here self-approves, which protects the key but not against a compromised builder submitting an artifact of its own.

Step 2, approval - automatic or four-eyes one variable picks which

A signing request has to be approved before the service will sign it. Which mode you get is decided by one variable, LAAVAT_APPROVER_TOKEN_FILE, and both modes are legitimate - they answer different questions.

set the variable

Auto-approval

The build approves its own request and never blocks. This is what every example in this repo does, and what makes make qemu-demo a single unattended command. Use it for CI, nightly builds and development.

Still use a token belonging to a different principal than the requester - otherwise the approval step records nothing meaningful. And be clear about what this mode does not buy you: it keeps the key safe, but it does not stop a compromised build from getting an attacker's artifact legitimately signed. Only four-eyes does that.

leave it unset

Four-eyes

The build blocks until a human approves, up to LAAVAT_SIGN_TIMEOUT (30 minutes by default). Production release builds typically want this: a person, not a pipeline, decides that these exact bytes get the product's signature.

Raise the timeout if approval routinely takes longer than the wait.

One trap worth knowing before you split dev from release. The approver token is a path, and paths are deliberately kept out of the task hash - otherwise moving your token file would re-sign everything and spend a fresh approval on bytes that did not change. The consequence is that approval mode is not part of the hash either: if a self-approving CI build and a four-eyes release build share one sstate mirror and the same operation id, the release build can be satisfied from the cache and no human ever sees those bytes. Give release builds their own operation, their own sstate, or both.

A timeout is not a lost request. If the wait runs out, the request stays alive on the service. Approve it and re-run the task: the log says resuming signing request <id>, meaning the same request was picked up rather than a second one opened. The same resume covers an expired token or an interrupted CI job - which is why the resume state deliberately lives outside the recipe's work directory, where a clean would otherwise destroy it.

Of a 28-line layer, 7 lines are layer.conf and about 15 are the meta-rauc bundle recipe anyone adopting RAUC writes anyway. The signing itself is the remainder: a guarded inherit per target, two or three board facts a class cannot discover, and one CA pin. The QEMU layer is the largest because it also ships the emulated machine's own quirks - a U-Boot config fragment and a tools install the demo harness needs - none of which is signing.

Two of those lines, verbatim the whole integration of a target

Trusted-application signing on optee-os, from the QEMU sample layer. The guard is the test-bed's, so one tree builds every tier with and without signing; a layer with one policy writes the bare inherit:

inherit ${@'laavat-optee' if d.getVar('LAAVAT_OPTEE_SIGN') == '1' else ''}

The boot image on the Variscite tier. This is the only target that ever needs more than the inherit, and only because an i.MX BSP routinely builds several boot images from one recipe and the class refuses to guess which one ships:

inherit ${@'laavat-hab' if d.getVar('LAAVAT_HAB_ARCHIVE') == '1' else ''}
LAAVAT_HAB_IMAGE       = "${S}/${BOOT_IMAGE_SD}"
LAAVAT_HAB_DEPLOY_NAME = "${UUU_BOOTLOADER}"

Everything else - finding the binary, reading the IVT block addresses back out of it, rendering the request, packing, unpacking, the resume state, the digest checks - belongs to the class or to the client, and none of it is yours.

What lives where, and why the rule that keeps the layer thin

A build layer that grows its own signing client ends up as a second implementation of someone else's protocol, and a second implementation drifts from the first. One rule keeps that from happening here: if it would pass a unit test with no bitbake stub, it is not the layer's.

Kind of knowledgeFor exampleWhere it lives
Build-system gluewhich task runs when, guarded inherits, where a signed file is installedmeta-laavat - ten classes and two shared helpers, every task a shell function, and nothing else in the layer at all
Protocol and transportupload, resume, approval, waiting, both digest checks, install, archive packing, HAB request renderingsigning-tool, as the verbs sign, pack, unpack and hab-request - one implementation, shared by every caller and released on its own
Format knowledgewhere an IVT sits in a boot image, what a .bif meansthe service, wherever it can be - it parses the .bif itself, so a BIF setting like bh_auth_enable is read by the tool that acts on it. i.MX IVT offsets are read out of the image by the client, because they are a property of the built binary rather than of the recipe

What keeps it that way is a test, not a convention: tests/test_layer_shape.py in the layer fails if any class grows a python do_* task or a def, if a parse-time block reads a LAAVAT_* variable, or if a class passes the client a flag its real argument parser does not have. It needs no bitbake, so it runs in ordinary CI.

which client the classes need

The classes call signing-tool, the LAAVAT client, which owns the round trip. It is public on PyPI, and the layer's own recipe builds it from there - 3.11.0 - so the build provides its own client and there is nothing to install or stage. To use a different build of the client (a pre-release, a fork), add a recipe at your own PV and select it with PREFERRED_VERSION_signing-tool. A client too old for the layer is caught by the first signing task, which names the version it needs, so this fails loudly rather than silently.

What kas and kas-container are the one piece of jargon that matters

kas is a Siemens tool that describes a whole Yocto build - which layers, at which commits, which machine, which local.conf lines - in one YAML file. kas build kas/all.yml replaces "clone eight repos, write bblayers.conf, source the environment, run bitbake".

Configs compose, which is the part worth internalising here: every tier in this repo is the same tree with a different config selected. kas/all.yml is kas/base.yml plus one fragment per feature; the service-signed tier is that plus the LAAVAT fragments. Nothing is branched or copied.

kas-container is a shell script that runs kas inside a container image that already has a working build host in it. That is why your machine needs so little. The script is vendored in this repo, byte-identical to upstream tag 4.7, so you do not install kas either.

Coming from repo and oe-init-build-env? A kas config is a manifest and a local.conf fused into one file. make shell still drops you into an ordinary bitbake environment inside the container if you would rather drive it by hand - bitbake, bitbake-layers, devshell and the rest all behave normally in there.

STEP 2

Get it and build it

#

Three paths, each adding one requirement to the last. Start at the top; if the last one fails, the earlier ones tell you which half broke.

Path A | no account

Build it

A complete i.MX8MM image with every signing path on, using local development keys. Proves the BSP and the wiring.

Path B | no account

Sign one artifact

Three checks, still without an account: the client's verbs against a stub, a real bitbake build with signing skipped, and the signing task end to end against the stub inside the container.

Path C | needs a service

The demo

Builds against a live LAAVAT service, boots the result and asserts what the boot proves - then requires tampered artifacts to be refused.

# get the tree, the pinned BSP layers, and the layer itself
git clone https://github.com/laavat/meta-laavat-testbed.git && cd meta-laavat-testbed
make fetch                 # also generates the throwaway RAUC dev keys (make dev-keys)
make fetch-laavat          # github.com/laavat/meta-laavat at the pinned release, LAAVAT_REF (v1.0.0)
# optional: install your own checkout of the layer instead
# make fetch-laavat LAAVAT_SRC=/path/to/meta-laavat

# Path A - ~2 h, dev keys, no credentials of any kind
mkdir -p build/logs        # build/ is gitignored; the shell opens the redirect before make runs
setsid nohup make build > build/logs/v1.log 2>&1 &

# ...then, once that build has finished (tail -f build/logs/v1.log)
make verify          # PASS/FAIL/SKIP per component; a SKIP fails too where the tier requires it

# Path B - still no account, no network beyond source fetching
make stub-smoke      # seconds, on the host: every client verb the classes call, the key pin both ways
make skip-smoke      # real bitbake: a signing target through do_deploy with LAAVAT_SIGN_SKIP set
# then the signing task end to end against the stub inside the container: six lines, RUNBOOK.md "Path B"
where the layer comes from

meta-laavat is public at github.com/laavat/meta-laavat. make fetch-laavat clones it into layers-50/meta-laavat and checks out the pinned release named by LAAVAT_REF (default v1.0.0), so it is an ordinary pinned layer like every other. LAAVAT_SRC is only for working on the layer itself: point it at a local checkout directory and that is installed instead.

why setsid nohup

A Yocto build killed mid-compile leaves truncated object files, and the next run fails with a bogus "undefined reference" in openssl or sqlite3 that looks like a source problem and is not. Detaching it means closing your terminal cannot do that.

Path A needs no LAAVAT account and no signing credentials: the RAUC dev keys are generated locally by make dev-keys (run automatically by the build targets) and marked throwaway, the FIT key is generated by poky on first build, and the HAB dev PKI is fetched from a public repository. Path B swaps the service for scripts/laavat-stub.py. Path C is make qemu-demo, and it is the only one that needs your own LAAVAT service account: its API URL, token files, a product/operation pair and key pin per target - the committed kas/qemu-live.yml holds placeholders for all of them - and a way for the build container to reach the service. Extra container arguments pass through KAS_RUNTIME_ARGS, for example make qemu-demo KAS_RUNTIME_ARGS="--network=host". RUNBOOK.md has all three written out in full, with the credentials and container-networking details.

First-run failures, and what they actually mean the ones that cost real time
SymptomCause
Signing task did not run on a rebuild, no errorUsually correct behaviour, not a failure. do_laavat_sign has no sstate of its own, so when the task that consumes its output (do_deploy, usually) is restored from the cache, the signed bytes come back with it and the signing task is properly skipped. Every signing task reads LAAVAT_SIGN_SKIP in its own shell body, so a cache object built with signing skipped has a different task hash and can never satisfy a signing-on build. Running -c laavat_sign by hand re-signs, and spends an approval, without changing the deploy directory - so it is the wrong reflex on a warm build.
LAAVAT_TOKEN_FILE must point at a readable token fileThe variable is set in your shell but bitbake dropped it. bitbake empties a task's environment and repopulates only what it was told to keep - add it to BB_ENV_PASSTHROUGH_ADDITIONS.
digest mismatch for <request>A corrupted or substituted download, not a configuration mistake: the client checks the reported digest against both the raw and the base64 form of what it fetched, so there is no encoding left to set wrong. Nothing was installed. Re-run; if it repeats, look at the request server-side before spending another approval.
the signing-tool on PATH is too old for this layerSomething overrode the client version down from the layer's own recipe (3.11.0). TIERS

What changes between dev keys and the service

#

The same tree builds every tier; the tier is the config you select. That makes the difference between "signed with a key on the build machine" and "signed by the service" small enough to read in full - and make delta prints it from the configs themselves, so it cannot drift from what the build does.

WHAT IT PROVES

The chain the demo builds

#

make qemu-demo boots the image it just built and reads the answers out of the serial log. This is where the three runtime-verified classes above are checked: for each one the key the device checks against is the service's and nothing else. They are not all checked at the same moment, which is the distinction the diagram draws.

who is actually doing the checking

Worth being precise about, because "the vendor's test suite says the vendor's product works" is the obvious objection. The verifiers here are not ours: U-Boot's own FIT verification, the OP-TEE core's own TA signature check, rauc info, OpenSSL's pkeyutl -verify, and poky's fit_check_sign on the i.MX tier. What this project wrote is the harness that drives them and reads their verdict out of the log - the pass/fail lines are those tools' answers, not ours.

the line that carries the weight

Verifying Hash Integrity ... sha256,rsa2048:laavat+ OK

laavat there is only a key name. What makes it meaningful is which key sits behind it - the certificate in that device tree carries the SignKernel operation's public key, as fetched from the service during the build.

What a passing run prints thirteen assertions, three boots 
--- boot 1: the checks ---
  optee-present          PASS
  supplicant             PASS  241
  ta-present-signed      PASS
  ta-load-signed         PASS  TEE test application done!
  ta-reject-foreign      PASS  refused: TEE test application done!
  bundle-verify          PASS  rauc-Message: No data directory or status file
  bundle-reject-devkey   PASS  refused: rauc-Message: ...
  bundle-reject-tampered PASS  refused: rauc-Message: ...
  uboot-fit-verified     PASS     (firmware log)
  optee-initialised      PASS     (firmware log)

--- boot 2: the TA tamper, alone in its own boot ---
  ta-reject-tampered     PASS  refused: TEE test application done!

--- boot 3: one byte of the kernel flipped ---
  Verifying Hash Integrity ... sha256 error!
  Bad hash value for 'hash-1' / Bad Data Hash / ERROR: can't get kernel image!
  uboot-fit-refused      PASS     (firmware log)
  fit-tamper-refused     PASS     (tampered kernel never reached userspace)

Why three boots and not one. The TA tamper needs a boot to itself, for two measured reasons: the corruption must land before anything loads the trusted application, because the core keeps a loaded one resident and would serve that copy; and refusing a corrupted TA sometimes wedges the supplicant, which would block every later check. One boot cannot satisfy both.

Each tamper is deterministic, and each is verified to have actually changed the file before the boot that must refuse it - the TA tamper by cmp, the bundle and kernel tampers by inverting a byte, which cannot silently do nothing. A negative test that quietly corrupts nothing passes for the wrong reason, which is the one way a table of PASS lines can be worthless.

THE TRAP

Deposit beside, or replace

#

This is the mistake worth knowing before you wire anything, because it produces a green build and a signed file and still leaves you with nothing.

ArtifactWhat the class doesSo the file you ship is
Kernel FITReplaces. laavat-fitkey writes the signed FIT back over the copy poky installs into the sysroot - the one U-Boot's build-time check and the deploy step both read.the only one there is
Trusted applicationsReplaces. do_laavat_unpack writes each signed .ta over its build-tree original before the unmodified do_install packages whatever is on disk.the only one there is
Boot image (HAB, AHAB, bootgen)Deposits beside. The signed image lands in the deploy directory as <name>.laavat-signed, next to the one your BSP's own signing produced.yours to choose - the .laavat-signed file, and your image recipe has to pick it up
Update bundleDeposits beside. Same shape: <bundle>.raucb.laavat-signed beside the dev-key bundle do_bundle built.yours to choose - deploy the .laavat-signed one; a device with the service CA refuses the other

Two replace and two deposit beside, so for half the targets the last step is yours. That is deliberate - a boot image and an update bundle are things you flash and publish, and the layer does not overwrite them behind your back - but it means "the build went green" is not the same as "the signed artifact is the one that ships." The demo proves the device refuses the wrong bundle; nothing can prove you deployed the right one but you.

THE DEV KEYS

So what happens to the R&D keys?

#

The obvious question once you know the service signing is additive. The answer is per artifact, and three of the four already trust the service and nothing else - "sidecar" describes where a file lands, not necessarily what the device trusts.

ArtifactDev key on the i.MX tier todayTo finish the job
Trusted apps Already gone. optee-os signs each .ta with its in-tree throwaway during the build, and do_laavat_unpack overwrites every one of them with the service-signed copy before packaging. The key the core embeds as its anchor is the service's, pinned by digest. Nothing - this one is done.
Update bundle Anchor already switched. The dev key still signs a bundle during the build - that is RAUC's own recommended shape, sign cheaply then re-sign - but the device keyring installed into /etc/rauc/ca.cert.pem is the service's issuing CA, pinned by digest. A dev-key bundle would be refused on the device. Deploy the .laavat-signed bundle, not the one beside it. The demo proves the device refuses the wrong one.
Kernel Anchor already switched. laavat-fitkey signs fitImage-none in place - the copy poky installs into the sysroot and U-Boot verifies - and laavat-fitkey-uboot puts the service's key into the control device tree this board appends. Nothing - this one is done.
Boot image Dev PKI, and it is a public one - var-hab-certs, which anyone can download and sign with. On this tier the boot image's signature exercises the mechanism; the security comes from the two steps beside this one. Point CST_CERTS_URI at your own PKI, and ultimately fuse your SRK hash into the chip. That last step is irreversible per device, which is exactly why the test-bed does not do it.
for your own build

None of the keys this repo uses should survive into a product. The RAUC dev CA and its signer are not committed: make dev-keys (scripts/gen-dev-keys.sh, run automatically by the build targets) generates them on first use as self-signed throwaways whose common name reads DO NOT USE IN PRODUCTION, and they are gitignored. That is what lets anyone build the "before" tier without credentials. The service-ca.pem every tier installs as the device's update root of trust is a committed placeholder in testbed-fixtures/files/dev-keys/, pinned by digest so the build passes. In your build, replace that file and its pin together with your service's issuing CA, replace the dev keys with your PKI, and let the service hold every key that matters.

YOUR TURN

Where your code goes

#

When you move this to your own board, the split below is the thing to understand: meta-laavat knows about signing and nothing about machines. Every "which file, which recipe, which product id" decision lives in a glue layer you own.

What one wired target actually looks like one line for most, two halves for the kernel

Most targets: one inherit

A class per target carries the mechanism - which file to pick up, how to package the request, where the result lands. The RAUC bundle is laavat-rauc on the bundle recipe with laavat-rauc-keyring and a CA pin on the recipe that owns /etc/rauc; trusted applications are laavat-optee on optee-os; a HAB, AHAB or Xilinx boot image is laavat-hab, laavat-ahab or laavat-bootgen on the recipe that builds it. Verbatim examples are under how light it is. The ids go in your configuration: 

LAAVAT_PRODUCT_ID:pn-optee-os    = "<product-uuid>"
LAAVAT_OPER_ID:pn-optee-os       = "<operation-uuid>"
LAAVAT_PUBKEY_SHA256:pn-optee-os = "<sha256 of the DER SubjectPublicKeyInfo>"   # the TA anchor, pinned

An operation with no class yet

The engine is still there for it. Say which file goes up, which operation signs it, and where the result lands - then put the task in the recipe's graph: 

inherit laavat-sign

LAAVAT_SIGN_OPERATION = "SignUBoot"
LAAVAT_SIGN_INPUT  = "${B}/u-boot.imx"
LAAVAT_SIGN_OUTPUT = "${WORKDIR}/laavat/u-boot.imx.signed"

addtask laavat_sign after do_compile before do_deploy

do_deploy:append() {
    # replace, don't deposit beside - see "the trap" above
    install -m 0644 ${LAAVAT_SIGN_OUTPUT} ${DEPLOYDIR}/u-boot.imx
}

The kernel, which needs both halves

do not use the shape above for the FIT

Signing the kernel FIT and stopping there is half a chain of trust. U-Boot verifies the kernel against whatever public key sits in its control device tree - and while that is still your build's own key, the service's signature is never checked and the boot is anchored to nothing. Worse, U-Boot verifies a copy in its own sysroot, not the deployed file, so replacing only the deployed fitImage leaves it checking a placeholder signature: invisible under QEMU, a build failure on a real board.

Two dedicated classes do both halves through machinery poky already has. On your kernel recipe:

inherit laavat-fitkey      # Yocto 5.2 and earlier. On 5.3+ the FIT has its own recipe: inherit laavat-fitimage on linux-yocto-fitimage

and on your u-boot recipe, on every release:

inherit laavat-fitkey-uboot

then, in your configuration:

LAAVAT_PRODUCT_ID:pn-linux-<yours> = "..."
LAAVAT_OPER_ID:pn-linux-<yours>    = "..."
# not per-recipe: both halves read it, and the u-boot recipe cannot see a :pn-<kernel> override
LAAVAT_FIT_PUBKEY_SHA256 = "<sha256 of the DER SubjectPublicKeyInfo>"

# the signed FIT is read from and written into the kernel's workdir, and the u-boot half
# reads it from there too; rm_work would delete it while the stamps still say it is done
RM_WORK_EXCLUDE += "linux-<yours>"

The kernel half signs the FIT with SignKernel and writes the service's certificate where poky already looks for a FIT signing key; the u-boot half injects that key into the control device tree instead of re-signing with a key the service does not hold. Both are required, and the class turns poky's "verified boot won't be available" warning into an error - a green build with an unverified kernel is the exact failure this layer exists to prevent. Needs kernel-fitimage in KERNEL_CLASSES and UBOOT_SIGN_ENABLE = "1"; both are checked at parse time, and on Yocto 5.3 or later laavat-fitkey stops the parse and names its replacement.

WITHOUT KAS

Getting the layer into your build

#

Everything above uses kas because this test-bed does. Nothing about meta-laavat requires it. The layer is an ordinary Yocto layer, and whatever you use to assemble a build - hand-written bblayers.conf, repo manifests, submodules, your own CI image - ends at the same three facts.

The three requirements, and how to satisfy them in any tooling no kas needed

1 | The layer is on disk somewhere bitbake can read

Vendor it however you vendor layers. It has no submodules and no build step of its own; a directory is enough. It is public at github.com/laavat/meta-laavat: clone it at a release tag wherever your other layers live, the way make fetch-laavat does here.

2 | Its path is in BBLAYERS

Plain OE, from an initialised build directory:

. oe-init-build-env
bitbake-layers add-layer /path/to/meta-laavat
bitbake-layers show-layers        # 'laavat' should now appear

or add the path to BBLAYERS in build/conf/bblayers.conf by hand - that is all add-layer does. With kas it is a repos: entry; with repo or submodules you place it and then add the path the same way.

3 | Its dependencies are present, on a series it supports

The layer declares exactly this, and bitbake enforces it at parse time:

LAYERDEPENDS_laavat       = "core meta-python"
LAYERSERIES_COMPAT_laavat = "scarthgap styhead walnascar whinlatter wrynose"
BBFILE_PRIORITY_laavat    = "6"
LAYERVERSION_laavat       = "3"

core is poky's meta; meta-python comes from meta-openembedded and supplies the client's Python dependencies. On a series that is not listed, bitbake refuses to parse and names LAYERSERIES_COMPAT in the error - it fails loudly rather than subtly. There is no addpylib: the layer ships no Python for bitbake's workers to import. LAYERVERSION is bumped when a change here needs a matching change in a layer that inherits these classes.

Where to put the configuration values and the per-recipe override form

The LAAVAT_* variables are ordinary bitbake variables. Put them wherever your project already puts configuration - local.conf, your own distro or machine .conf, a .bbappend, or a kas local_conf_header. The layer does not care which.

Site-wide values (the API URL, the token paths, the CA bundle) are set once. The ids differ per artifact, so those take the :pn- override form, which targets one recipe: 

LAAVAT_API_URL    = "https://signing.example.com/api/v1"
LAAVAT_TOKEN_FILE = "/secure/path/token.jwt"     # a path, never a token

LAAVAT_PRODUCT_ID:pn-linux-yourbsp = "..."
LAAVAT_OPER_ID:pn-linux-yourbsp    = "..."
LAAVAT_PRODUCT_ID:pn-u-boot-yourbsp = "..."

If you export the token path from your shell instead, bitbake must be told to keep it - it empties a task's environment and repopulates only what it was told to preserve: 

export LAAVAT_TOKEN_FILE=~/.laavat-token
export BB_ENV_PASSTHROUGH_ADDITIONS="$BB_ENV_PASSTHROUGH_ADDITIONS LAAVAT_TOKEN_FILE LAAVAT_APPROVER_TOKEN_FILE"

One kas-specific ordering trap, if you do use kas: it emits local_conf_header sections in alphabetical key order, so a section whose key sorts later wins on plain assignments. Name your section accordingly, or use :pn- overrides, which win regardless of order.

Proving it landed, before you wire anything three checks that cost seconds 
# 1. the layer is in the build
bitbake-layers show-layers | grep laavat

# 2. the client recipe resolves, at the version the classes require
bitbake -e signing-tool-native | grep '^PV='        # 3.11.0, from the layer's recipe, unless you chose another

# 3. your recipe sees the values you set
bitbake -e <your-recipe> | grep '^LAAVAT_'

Check 3 is the one that catches most mistakes: a :pn- override on the wrong recipe name, a value shadowed by ordering, or a variable that never reached bitbake at all.

And the negative control, which is the reassuring one: on a build where no recipe inherits a laavat class, bitbake -e <recipe> shows zero LAAVAT_* variables and no do_laavat_* task. Adding the layer to a working BSP cannot change its output until you ask it to.

the one thing that is not optional

Signing happens during the build, so the machine running bitbake needs egress to the API and to the storage URLs it hands back. BB_NO_NETWORK does not stop it - that only gates the fetcher - so treat "offline builds do not sign" as a policy you enforce, not something the layer enforces for you.

Vocabulary

#

Terms this repo will throw at you, shortest useful definition first.

Yocto and build-system terms layer, recipe, bbappend, sstate, kas
layer
A directory of recipes and configuration bitbake includes. Adding one changes nothing until something uses it.
recipe / .bb
Instructions to fetch, build and package one component.
bbappend
A file that adds to a recipe someone else owns, without editing it. How signing gets attached to a vendor's kernel.
class / .bbclass
Reusable recipe logic. A recipe inherits one to gain its tasks and variables.
task
One step in a recipe's build, like do_compile. Signing adds one of its own.
sstate / setscene
bitbake's cache of finished task output. A setscene "hit" restores a result instead of rebuilding - and can skip a task that a cached one covers, which is why signing tasks are run by name.
kas
Describes a whole build - layers, commits, machine, local.conf - in one composable YAML file.
kas-container
Runs kas inside a container that already has a build host in it, so yours needs almost nothing.
machine
The board a build targets. Here: ten of them, from imx8mm-var-dart to zynqmp-generic; qemuarm64-secureboot is the one that boots.
deploy dir
build/tmp/deploy/images/<machine>/ - where finished, flashable artifacts land.
Secure-boot and signing terms FIT, HAB, TA, RAUC, dm-verity
FIT image
Flattened Image Tree: kernel, device trees and signatures in one file U-Boot can verify before booting.
control DTB
U-Boot's own device tree. The public key it verifies the FIT against lives here - which is why placing that key is half the job.
HAB
i.MX High Assurance Boot: the boot ROM checks each stage's signature against a hash fused into the chip.
IVT / CSF
The header at the start of each i.MX boot stage, and the block holding the signature the ROM checks.
SRK
Super Root Key. Its hash is burned into chip fuses and anchors the whole HAB chain - irreversibly, which is why fusing is not done here.
TF-A / BL31 / BL33
Arm Trusted Firmware and its boot stages: the secure monitor, and the normal-world bootloader it hands off to.
OP-TEE / TA
A trusted execution environment running beside Linux, and the Trusted Applications it loads - each verified against a key compiled into its core.
RAUC
An A/B update framework. A .raucb bundle is signed, and the device verifies it against a keyring before installing.
dm-verity
Block-level integrity for the root filesystem; its root hash sits inside the signed FIT.
HSM
Hardware security module. Holds private keys - the service generates its signing keys there as non-exportable - and performs signatures inside itself.
product / operation
The LAAVAT service's two identifiers. A product groups operations; an operation is one signing capability with one key behind it.
four-eyes approval
A signing request must be approved by someone other than the requester before the service will sign.
OPERATIONS

The questions a risk review asks

#

Moving signing into a service moves a dependency into your build. These are the consequences worth knowing before you commit to it, including the ones your own deployment decides.

What happens when the service is unreachable mid-build answered from the code

The build fails - there is no unsigned fallback, by design. What matters is whether it fails recoverably, and the resume state is what decides that. It is written as soon as the service returns a request id, lives outside the recipe's work directory, and is deleted in exactly one case: the service terminally rejects the request.

FailureWhat a re-run does
Unreachable during uploadNo request was created and no state written. The re-run submits cleanly - there is no orphan to clean up.
Unreachable during downloadState survives, so the re-run prints resuming signing request <id> and picks up the same request. Approval is not spent twice.
Token expired mid-runSame as above - write a fresh token to the same path and re-run; the request is resumed, not duplicated.
Approval timed outThe request is still alive. Approve it and re-run.
Service rejected itState is cleared. The re-run starts a new request, which is the right behaviour for a rejection.

One edge case the client handles explicitly rather than silently: if the request is created but its state file cannot be written, the error names the request id, so a request that would otherwise be stranded is recoverable by hand.

Air-gapped builds there is no offline mode

Signing happens during the build, over the network, and there is no offline or batch path today, so build hosts with no egress are not supported. If that is your environment, it is a product conversation rather than a configuration one. Be aware too that BB_NO_NETWORK will not stop a signing task - it gates the fetcher, not a task's own subprocess - so "offline builds do not sign" is a policy you enforce, not something the layer enforces for you.

Key rotation, revocation and old builds what the layer pins, and what your PKI owns

Rotation is fail-closed, deliberately. Every verification key this layer embeds is pinned by the SHA-256 of its DER SubjectPublicKeyInfo, so a rotated key does not quietly become the new anchor of everything you ship - the fetch fails and the build stops until someone updates the pin on purpose. That is the whole reason the pin is mandatory and has no default.

Revocation of a boot-ROM root key is the silicon's mechanism, not ours. On i.MX that is HAB's SRK revocation via fuses; nothing in this layer changes or can change it.

Three questions belong to your deployment rather than to this layer, and are worth putting to whoever operates your LAAVAT service, because the answers are specific to it: reproducing a signature years later, how long product and operation ids stay stable, and what happens to already-shipped devices if a production key is compromised.

Tokens in CI, and distribution what to plan around

Tokens are short-lived and the lifetime is set by your deployment, not by this layer - so treat a token as per-run credential material: mint one at the start of a pipeline job and write it to the path LAAVAT_TOKEN_FILE names. A long-running job that outlives its token gets an authorization error, and the recovery is a fresh token plus a re-run, which resumes rather than duplicates. The layer only ever reads the file, so refreshing it in place works.

The layer is public, at github.com/laavat/meta-laavat, in tagged releases; pin one, as make fetch-laavat does with LAAVAT_REF. It is plain Yocto with no binary blobs, so it is auditable in full. Its network use is specific and worth listing for a firewall review: the client recipe fetches signing-tool and its dependencies from PyPI like any other source fetch; the signing tasks call the service's API (fetching public keys to check against their pins, and opening, polling and downloading signing requests); and they upload and download the artifacts themselves through the storage URLs the service hands back. The client is a separately released component - signing-tool, public on PyPI - so the half of this that talks to the service is versioned and auditable on its own. For anything else, contact Laavat at contact@laavat.com or laavat.io/contact.

what the runtime proof covers

It runs on qemuarm64-secureboot, an emulated machine, and what it demonstrates is that the glue, the anchors and the formats verify at runtime against the service's keys. The boot-ROM half of the chain is the part it cannot reach: an emulator models no fuses, so HAB, AHAB and the Xilinx CSU can only be exercised on silicon. Bringing that half up on your own board is real work, and it belongs in your plan.
